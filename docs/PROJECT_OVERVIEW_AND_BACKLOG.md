## 一、这个软件是什么

**爱管理**是一个面向软件项目全生命周期管理的 AI 协作平台。它不是"项目管理工具加个 AI 按钮"，而是把项目管理里最依赖人的三件事交给 Agent：**开好会、看清风险、守住代码质量**。

核心主张一句话：

> 所有 Agent 都不直接改数据。它们只产出建议（Proposal），人工确认后由统一执行器落库，全程留审计痕迹。

这条主张决定了整个架构，也是我们和"AI 玩具"的分界线。

## 二、整体结构：一心一环三 Agent

```
                    ┌───────────────────────────────┐
                    │   一心：决策与审计中心           │
                    │   Proposal 协议 + 统一执行器    │
                    │   + ChangeHistory 双层审计      │
                    │   + 会议记忆 / 计划版本         │
                    │   （会议侧与事件侧共用，已冻结）  │
                    └───────────────┬───────────────┘
                                    │ 只建议，不直写
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
┌───────────────┐        ┌───────────────┐        ┌───────────────┐
│ Agent 1       │        │ Agent 2       │        │ Agent 3       │
│ 会议主持       │        │ 风险分析       │        │ 代码分析       │
│ 控流程·控时间  │        │ 多侧面扫风险   │        │ 监察 AI 代码   │
│ 纠偏·出纪要    │        │ 出处置建议     │        │ 重构知识库      │
│ 【已做主体】   │        │ 【已完成】     │        │ 【未开始】     │
└───────────────┘        └───────────────┘        └───────────────┘
        └───────────────────────────┼───────────────────────────┘
                                    ▼
                    ┌───────────────────────────────┐
                    │  一环：外围小 Agent（按需挂载）   │
                    │  纪要导出 · 负载容量 · 材料生成    │
                    │  数字成员 · 贡献洞察 · 报表        │
                    │  状态见第三节，逐条核实过         │
                    └───────────────────────────────┘
```

三个 Agent 之间的协作方式：**共用同一套 Proposal 协议与执行器**。会议里决定要做的事，和扫描出来的风险，出现在同一个待确认中心（顶栏铃铛），人一次审完。`origin` 字段区分来源（`meeting` / `event`），协议本身完全一致。

#### 六类风险规则速查（组长快速理解用）

扫描入口：`detectProjectEvents(state, sprintId, 参考日期)`，纯确定性，
不调模型，输入相同输出永远相同，结果按严重程度排序（高→中→低）。

| # | 风险类型 | 触发条件 | 判定算法 | 升级为高风险的条件 | 处置方向 |
|---|---|---|---|---|---|
| 1 | 期限风险 | 未完成 且（已逾期 或 ≤1天到期且进度<80%） | 剩余工时 = 估算×(1−进度)；剩余工时 = ceil(估算×(1−进度/100)) | 逾期 或 在关键路径上 | 确认拆分或调整排期 |
| 2a | 依赖阻塞 | Sprint 内任务的前置任务未完成 | 沿依赖表找出未完成前置；附带算跨 Sprint | 前置为 blocked / 跨 Sprint / 在关键路径 | 联系前置负责人，评估连带影响 |
| 2b | 阻塞传播链 | 同 2a | 从被阻塞任务广搜，算出会连带影响的后续任务 | 同上 | 评估连带任务排期 |
| 2c | 循环依赖 | FS 依赖在 Sprint 子图内成环 | DFS + 三色标记找环 | 天然高风险 | 移除一条依赖 |
| 3 | 成员负载 | 剩余工时 > 周期可用容量 | 可用容量 =（周容量/5）× Sprint 工作日数（排掉周末，date-fns 算） | 超出 120% | 转派 / 拆分 / 调范围 |
| 4 | 范围容量 | Sprint 内 Story Point 之和 > 容量 | 累加 Story Points 与 capacity 比 | 超出 120% | 移出低价值 Story 或拆下轮 |
| 5 | 成果缺失 | 状态为 review/done，但无成果说明、无提交时间 | 检查 resultSummary 与 submittedAt | done 却无成果（更严重） | 补充成果或退回继续执行 |
| 6 | 验收缺失 | Sprint 内 Story 验收标准数为 0 | 计数验收标准 | —（固定中风险） | PO 补验收标准 |

**每条风险都带**：严重程度、触发规则、判断依据（原始数据）、归因对象（task/story/sprint/member + ID）、处置方向。
**共性设计**：确定性可核对、证据可追溯、规则间互不影响、按严重度排序。

**从检测到处置的链路**（这是事件 Agent 的核心价值）：

```
detectProjectEvents → 6 类 DetectedEvent（纯事实，不改数据）
      ↓ 用户在某条事件卡点"生成建议"
buildAction        → 翻译成 ProposalAction，带 precondition 记住当前状态
      ↓ 用户勾选采纳
applyProposal      → 拓扑执行 + 复验 precondition
      ↓ 数据变了 → stale 阻断；没变 → 写回
Store Action + ChangeHistory → 双层审计
```

## 四、爆破点：会议 Agent 纵向做深

老师要求"倒梯形，功能面广已经做出来了，找一个点做深"。会议 Agent 就是这个点——理由：

1. 会议是"爱管理"里最重的模块，已有一整套编排和纪要，**纵向加深不用重建地基**；
2. 会议类型化 + 计时 + 纠偏 + 语音，是一组**互相咬合**的功能：类型决定时长和流程，计时暴露超时，纠偏靠转写内容判断，语音是纠偏的数据源。做深之后是一条完整链，不是零散功能；
3. 演示效果直观：现场开一场站会，超时自动提醒、有人跑题当场被拉回、散会立刻出纪要并落库。

### 4.1 会议类型化（新增）

给会议加 `meetingType` 字段，每种类型一套流程模板与时长：

| 类型 | 时长 | 流程 |
|---|---|---|
| 站会 | 15 min | 每人 2 分钟：昨天/今天/阻塞，超时打断 |
| 评审会 | 60 min | 演示 → 反馈 → 验收决策，跑偏到实现细节时提醒回到验收标准 |
| 复盘会 | 45 min | 事实 → 原因 → 改进项，每条改进项必须落成任务或风险 |
| 规划会 | 90 min | 拆解 → 估算 → 容量校验，超容量阻断 |

改动点：`types.ts` 加字段 → `createMeeting` 接收类型 → `MeetingRoom.tsx` 顶部按类型渲染模板 → 新建会议入口提供类型选择。

### 4.2 计时与超时提醒（新增）

纯确定性，可信度最高：

```
会议开始记录 startAt → 顶栏显示倒计时（按类型取时长）
剩余 2 分钟黄色提醒 → 到时红色提醒 → 主持人可手动结束或延长时间
超时记录进会议记忆，作为复盘素材（"站会超时率"）
```

### 4.3 话题偏离检测（新增）

半可信，必须可推翻。方法依据：人机对话评估中的一致性（coherence）思想，
DSTC 对话系统评测一直把它作为核心维度；我们做的是面向会议场景的工程简化版，
不是学术创新。

```
阶段一（关键词版，半天可落地）：
  当前议题取自 topics（已有）→ 中文分词去停用词，得议题关键词集合
  每次发言（文本消息或语音转写）→ 同样处理
  最近 3 条发言拼成滑动窗口，重合度 = 交集 / 议题关键词数
  重合度低于 0.3 且连续 3 个窗口都低 → 生成"可能跑偏"提示（只提示，不阻断）

阶段二（embedding 版，有模型通道，多半天）：
  议题文本与窗口文本各取一次 embedding → cosine 相似度
  低于阈值触发；能处理同义词（"排期" vs "时间安排"），比关键词更准

纠偏机制（两阶段通用）：
  用户可点"没跑偏" → 该次不计入，后续阈值临时放宽
  提示语由模型润色，判定由规则做，模型不参与"是否跑偏"的决定
```

### 4.4 语音转文字 + 说话人标记（新增）

```
浏览器 Web Speech API（免费、零配置、Chrome 可用）
点击麦克风 → 实时转写 → 生成一条 MeetingMessage
说话人：当前登录用户（participantIds 已有）
开始/结束时间戳存进消息
转写内容进 topics 判定 → 喂给纪要 → 纪要里的"原话"是真语音转的
降级：麦克风不可用或识别失败 → 回退打字，按钮置灰并提示
```

**注意**：ninan.cloud 已调研，是端侧语音输入 App（输入法/全局快捷键），无 API/SDK，浏览器无法调用，不用再考虑。

## 五、Agent 3：代码分析（下一步，从零开始）

**定位**：不承诺"证明代码 100% 可靠"（做不到），而是**把不可靠的地方指出来并给出依据**。

三层证据链，每层可信度不同且可验证。方法依据：《重构》（Fowler）第二章的 22 种坏味道
自带"表现 + 成因 + 对应手法"，本身就是方法论；阈值标定（如"多长算过长"）引用
坏味道检测实证研究，不拍脑袋。

```
第一层  静态度量（确定性，可信）
        8 种可直接写成规则的坏味道：
          过长函数（行数阈值）→ 提炼函数
          过长参数列表（>4 个）→ 引入参数对象
          重复代码（文本相似块）→ 提炼共用
          过大类（方法数阈值）→ 提炼类
          发散式变化 / 霰弹式修改（一次改动触及多文件，用 git 历史算）
          数据泥团（总一起出现的参数组）→ 模式匹配
          基本类型偏执（大量裸 string/number 传业务含义）→ 启发式
          注释过多且代码难懂 → 注释代码行数比

第二层  知识库映射（引用，可信）
        《重构》坏味道 → 重构手法，用 RAG 检索书中原文支撑
        例：过长函数 → 提炼函数（Extract Function）
        阈值取值引用实证研究（如 code smell detection thresholds 方向），
        检索关键词：code smell detection thresholds empirical study /
        代码坏味道 阈值 实证

第三层  模型组织（解释，半可信）
        把前两层写成评审意见，每条必须绑定行号或度量值
        无依据的意见直接丢弃，不输出

输出    问题清单（严重程度 + 依据 + 建议手法）
        不用单一总分；如需打分，输出多维雷达且权重公开、人工可推翻
```

## 七、评估可信度设计（答辩会被问，先定好口径）

**原则：能数出来的给数字，要判断的必须带证据，单一分和绝对结论一律不给。**

| 结论类型 | 可信度 | 做法 |
|---|---|---|
| 会议超时、谁说了多久、谁阻塞了别人 | 可信 | 确定性统计，可逐条核对 |
| 任务逾期、风险等级、代码度量值 | 可信 | 规则算出来的 |
| 话题是否跑偏 | 半可信 | 阈值可调，允许用户推翻 |
| 会议纪要质量、代码坏味道判断 | 半可信 | 必须引用原文/行号，无依据丢弃 |
| "某成员贡献 87 分" | 不可信 | 不做。只给事实 + 雷达图，权重公开可调 |

被问到成员评估时，标准答复：

> "我们不做单一分数排名。系统给出的是可核对的客观事实——发言时长、交付任务数、
> 阻塞他人次数、代码度量趋势——再由模型基于这些事实写一段评语并标注引用。
> 权重公开、人工可调，评语可以被推翻。分数是管理者的判断，不是系统的结论。"

---

## 八、答辩叙事骨架

1. **一句话**：爱管理是 AI 协作的项目管理平台，三大 Agent 各守一域，共用一套建议审批与审计底座。
2. **架构**：一心（决策审计中心）一环（外围小 Agent）三 Agent（会议主持/风险分析/代码分析），倒梯形——广度已完成，爆破点在会议 Agent 纵向做深。
3. **可信度**：确定性规则打底，模型判断必须带证据引用，分数只做公开权重的多维雷达。
4. **边界**：不做的三件事都给了理由，体现工程判断而非能力缺失。
