## 一、Sprint 3 计划会纪要

### 1.1 背景与任务来源

Sprint 2 结束时，我产出了项目全景与任务清单 `PROJECT_OVERVIEW_AND_BACKLOG.md`，
其中第三节 3.2 对照代码把事件型 Agent 标为"我负责，已完成"，第六节按 P0/P1

事件侧在本实验认领的条目，来自两处口径（二者一致）：

| 来源 | 条目 | 本实验目标 |
|---|---|---|
| 待办清单 P1-8 | 教学事实面板 | 按成员聚合客观事实，供教学评估（**本实验核心交付**） |
| Sprint 2 回顾会 3.2 | 分析结果为快照语义，用户不易理解 | 明确"重算/快照"表达 |

边界：会议侧 P0-3（语音转文字）、P0-4（话题偏离）属会议主持侧能力，不在本文事件侧贡献范围。

### 1.2 需求提出：关键设计决策

**决策 1：成员视图只给事实，不给分数（本实验主线）**

承接待办清单"明确不做：成员排名打分"的立场。成员教学视图只陈列可核对的客观数字，
由管理者判断，系统不打分、不排名。理由：一旦系统给出"某成员 87 分"，答辩时会被追问
"凭什么 87"，答不上来就崩；只摆事实，永远可辩护。

**决策 2：快照就是快照，不能装作实时**

事件分析结果只反映扫描那一刻的数据。若不显式说明，用户会当实时监控，数据变了却不重扫，
进而误读。必须在产品内写清"某时刻的快照、数据变化后请重新分析"。

**决策 3："风险解除"要成为一种正向反馈**

修复数据后事件消失，是"问题解决了"，不是"功能坏了"。要求重算时对比上次扫描，
明确提示哪些风险已解除，杜绝静默消失造成的误判。

**决策 4：沿用"只建议、不直写"，不引入模型判断**

三项改进均为确定性能力，不改变已冻结的 Proposal 协议，不引入第二套执行器。

### 1.3 验收标准

1. TypeScript 类型检查通过、生产构建通过；
2. 成员客观事实结果稳定、不含 score / rank 字段；
3. 聚合口径与现有 `workloadAnalysis` 一致（按 Sprint 范围、叶子任务）；
4. 全量测试若有失败，须与本次改动无关（以去除改动重跑对比为准）。

据此做出三点判断：

1. 我的改进 2/3 是"会话内、不落库"，对方是"持久化生命周期 + 自动巡检"，对方更彻底，

   不一致。**最终基于 `origin/main` 最新基线重做**：复用其 `workloadAnalysis` /
   `selectMemberWorkload` 的 Sprint 口径，只新增聚合层，交付于 `feat/member-facts` 分支；

（代码位置 / 命令输出）；不盲目采纳。
