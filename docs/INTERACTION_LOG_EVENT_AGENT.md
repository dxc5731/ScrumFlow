# 事件型 Agent 开发交互记录（节选）

> 供材料撰写使用。记录摘自真实开发会话，按阶段整理。
> 引用为真实对话摘录，仅删减无关步骤、轻微顺稿，未改变原意；
> 标注"概括"处为对多轮对话的归纳，非逐字引用。
> 记录中"用户"为事件型 Agent 负责人，"助手"为 AI 编程助手。

## 阶段一：先对齐"这个 Agent 到底做什么"

**背景（概括）**：项目进入整合期，需要把事件型 Agent 的职责边界、
与会议型 Agent 的差异讲清楚，供分工与汇报使用。

**用户**：

> "我还是没太懂我到底做了啥，我理解的任务应该是做几个实现不同功能的agent，现在是嘛？"

**助手（概括）**：说明事件侧不是"多个独立小 Agent"，而是"六类监测职能 + 一套
审批执行机制"；六类监测分别是期限、依赖、负载、范围、成果、验收，
每类独立触发、独立证据、独立处置动作；诊断由确定性规则决定，
模型只负责措辞，执行走与会议侧共享的 Proposal 审批执行器。

**用户**：

> "没必要拆。"

**说明**：助手曾建议把单一扫描函数拆成 6 个独立文件以迎合"多 Agent"的表述。
用户判断规则之间互相独立、无需编排，拆分只是增加文件壳、行为不变，因此拒绝。
该判断成立：六条规则在代码中确实是并列、互不依赖的。

## 阶段二：设计原则的确立（这是整个 Agent 的地基）

**背景（概括）**：讨论事件检测结果如何落地，由此固定了四条贯穿全项目的原则。

**用户**：

> "生成一次建议后不是应该去执行状态面板选择它改变它的状态嘛，之后再回到sprint管理面板后原来的AI分析结果就都没了，还需要再点一次分析，是不是这个记录没保存啊"

**助手（概括）**：确认用户观察属实，并拆分为两类存储——
事件（扫描结果）只在内存、切页需重新分析；建议（Proposal）持久化、
刷新不丢，且重新分析后会自动按目标关联回面板。事件按当前数据实时计算，
任务状态改变后事件消失属于"风险解除"，是正确行为而非缺陷。

**由这次讨论确立的原则**：

1. Agent 只产出建议，不直接改项目数据；
2. 建议持久化，扫描结果可重算；
3. 执行前必须比对建议生成时的数据状态（precondition）；
4. 与会议侧共用同一套 Proposal 协议与执行器，不另起一套。

## 阶段三：真机验证——发现 6 个真实问题（材料中最有说服力的部分）

**背景（概括）**：功能完成后进行 6 步浏览器人工验证，覆盖扫描、生成、
执行写回、待确认列表、冲突校验、跨页面徽标。以下每条都是验证中真实发现的问题。

### 问题 1：AI 解读没显示（界面缺陷）

**用户**：

> "A，但是没有B。"
> （A=出现待确认建议卡，B=出现 AI 解读）

**定位**：解释请求已发出、数据也已返回，但界面组件漏写了渲染分支，
属于实现遗漏。**修复**：事件卡补充"AI 解读"渲染区与"生成中…"状态。

### 问题 2：状态文案歧义（UX 缺陷）

**用户**：

> "这里有个小问题，还没点生成建议就能看到最下面的一行紫色的小字是建议"

**定位**：规则模板的静态文案与按钮"生成建议"、模型"AI 解读"三层都叫"建议"，
容易误以为已经生成。**修复**：静态文案改名为"处置方向"，
形成"处置方向（规则）→ 生成建议（操作）→ AI 解读（模型）"三层区分。

### 问题 3：执行后没有出现预期的 stale（冲突校验验证）

**用户**：

> "换了一个测，并没有变成stale"

**定位**：先确认了操作顺序（必须先生成建议、再改任务状态、最后执行），
排除顺序因素后继续追查。

**用户**：

> "测的test-026-1 已逾期，从待开始到开发中，直接显示已写回项目"

**定位**：用户改的是看板上 Story 卡的交付状态，而 precondition 盯的是任务本身的
`status` 字段——Story 变了、任务没变，校验通过属于逻辑正确。
随后按"改任务本身状态"重测，命中预期。

**用户**：

> "不是显示stale显示的failed"

**定位**：动作层已是 stale，但整单状态在"0 项成功"时统一记为 failed，
两层状态混在一起造成误解。

**用户**：

> "显示已执行 0 项，失效 1 项"

**结论**：冲突校验（precondition）生效确认。随后追加展示层修复：
新增 `proposalStatusLabel`，全 stale 显示"已失效"、真失败显示"失败"，
契约值不动（保持与会议侧一致）。

### 问题 4：已完成任务仍显示"已逾期"（快照语义确认）

**用户**：

> "你看这，这个都完成了，还是显示已逾期，而且还有AI 1的红字"

**定位**：详情页的分析块是上次扫描的快照，任务状态改变后不会自动刷新；
甘特图徽标的红字来自另一条规则（成果缺失）。重新扫描后"已逾期"消失，
"缺少成果提交"为规则正确行为（状态已完成但无成果说明）。
**结论**：行为符合设计，非缺陷；文档中作为"快照语义"已知特性记录。

### 问题 5：徽标概念不直观

**用户**：

> "AI徽标是啥样的啊，没看见"

**处理**：说明徽标形态（按最高严重程度的红/黄/绿）、位置（甘特任务行、
看板 Story 卡）、悬停可看事件清单；并给出快速定位路径。

### 问题 6：验收标准与界面入口

**用户**：

> "看板上的任务都是us开头的"

**定位**：看板按 Story 聚合，工程任务在 Story 下。**处理**：给出甘特图、
用户地图两条可达路径，并更换测试对象继续验证，不在一处卡死。

### 验证收尾

**用户**：

> "过了，没问题"

**概括**：6 步验证全部通过，形成 `EVENT_AGENT_FINAL_REPORT.md` 中的验证章节。

## 阶段四：架构升级讨论（倒梯形、三 Agent、一心一环）

**背景（概括）**：老师肯定现有成果后提出新方向，要求"倒梯形——
功能面已广，选一个爆破点做深"。以下是架构讨论中的关键表述。

**用户**：

> "刚又聊了一下，我觉得又有了好多想法可以跟你梳理。老师提到，可以做成三个主要的agent，分别是会议主持、风险分析和代码分析……"
> "对于这个项目来说，老师希望是倒梯形的形状，功能面广已经实现了，剩下的就是找一个爆破点做深。"
> "可以分出不同的会议类型，比如站会、总结会等等，有不同的时间限制，有计时器提醒时间，主持人也会根据会议类型有不同的流程把控。"

**助手的回应（要点，概括）**：
- 爆破点建议选会议 Agent 纵向做深：已有编排与纪要地基，纵向加深不用重建；
- 类型化→计时→纠偏→语音是一条互相咬合的功能链，适合做深；
- 可信度分三层：确定性度量直接给数；模型判断必须带证据引用；
  单一分数与绝对化结论不做。

**用户**：

> "细节我就不看了，大方向上我们讨论的是对的就行……不过如果你觉得有必要，可以写进去，具体实现再说。"

**概括**：用户对架构方向做出判断后，授权将可信度分层、
方法论文支撑等设计原则写入文档，实现细节留待后续。

## 阶段五：论文与方法的主动规划

**用户**：

> "语音识别已经实现了。还要不要多找些论文做支撑，用里面的方法增加可信度"

**助手（概括）**：区分"需要论文"与"不需要论文"的功能——
工程实现（语音转写、计时器、规则扫描）不需要论文背书；
需要方法支撑的是半可信判断：话题偏离、代码坏味道、成员贡献度量。

**用户**：

> "不能现在就从论文里提取点方法，到时候按这个方法做吗"

**概括**：确立"方法先行、代码后到"的推进方式。随后形成三篇论文清单：
对话一致性（DSTC coherence）、代码坏味道阈值实证、团队效能度量框架，
并为每篇标注"找什么 / 用在哪 / 优先级"。

## 阶段六：工程协作细节

### 接入第三方服务的尽调

**用户**：

> "我们想的是直接接进来而不是复刻。"

**助手（概括）**：实地查看 ninan.cloud 后确认其为端侧语音输入 App
（输入法 / 全局快捷键），不提供 API / SDK，浏览器沙箱无法调用；
给出结论与替代路径（浏览器 Web Speech API / 讯飞 / Whisper），
并记入文档"明确不做"清单，附原因备查。

### 分支策略

**用户**：

> "推上去的话能不能不覆盖她的，单开一个分支啊比如"

**概括**：采用独立分支 `merge/event-plus-meeting` 推送合并结果，
`main` 保持不动，避免影响同伴正在使用的版本；合并前通过 PR 评审。

**用户**：

> "为啥contributor里没有我啊"

**处理**：排查确认为提交邮箱未绑定 GitHub 账号（提交作者本身正确），
指引在账号邮箱设置中绑定验证，历史提交会自动归属。

### 文档交付

**用户**：

> "能给我一整份md文档吗，我直接给组员看就行"

**概括**：产出 `PROJECT_OVERVIEW_AND_BACKLOG.md`（项目全景、已完成清单、
爆破点、待办、可信度口径、论文清单）与 `MERGE_NOTE_FOR_MEETING.md`
（合并说明，供同伴评审），并把"已完成"逐条对照代码核实，
避免把同伴已完成的项误标为待办。
