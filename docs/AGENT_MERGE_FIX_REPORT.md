## 原因与针对性修复

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 创建较多事件提案后，会议建议丢失 | 事件创建函数把共享 `proposals` 截断至最近 50 份；会议、消息和历史记录仍引用被删除的 ID | 移除共享持久提案的数量截断，保留审核与执行依据；验证待审核、已应用提案及导入导出后的引用完整性 |
| 同一事件再次扫描后生成重复提案 | 创建时保存 Sprint/Story 面板 ID，重扫时却按事件的任务 ID 查找 | 保存事件实际目标；识别旧数据中证据记录的目标，重扫和重新打开均恢复同一提案 |
| “全部采纳”撤销已采纳动作 | 按钮对每项做开关切换，`accepted` 被切回 `pending` | 对尚未执行的动作统一设为 `accepted`，重复点击保持一致 |
| 数字员工对容量问题答非所问 | 写入意图正则把“不修改”中的“修改”当作肯定请求，提前返回拒绝修改话术 | 排除否定的修改指令后判断真正的写入请求；容量回答明确列出本人未完成工时、剩余工作日、容量及余量；真正要求修改状态时仍拒绝代写 |
| 导出材料后的普通讨论误生成额外文件 | 上一轮 `material_organizer` 无条件作为下一轮活动助手继承 | 仅在明确材料请求或材料追问时继承材料助手；普通话题回到会议协调流程 |
| 原有 22 项测试失败 | 用例固定使用 2026 年 9 月的演示 Sprint，却用当前日期计算剩余容量；到 10 月后窗口为 0，方案与约束断言连锁失败 | 为八组规划用例固定场景日期为 2026-09-21；仅模拟 `Date`，异步计时器正常；两项专门验证过期场景的用例固定到 2026-10-03 |

22 项失败在原 `main` 与队友合并分支上完全一致，属于已有测试的时间漂移，并非队友合并删除了会议能力。修复未删除原断言、跳过用例、修改生产时钟或放宽生产容量校验。

另收紧 `UPDATE_DEADLINE`、`CHANGE_ASSIGNEE` 的目标校验：执行器仅支持任务目标，因此非法 Story 目标应在校验阶段明确拒绝，避免落入“任务不存在”的错误路径。
