# 事件型 Agent 最终报告

## 一、实现了哪些功能

### 1. 六类事件检测（确定性规则，离线可用）

| 规则 | 触发条件 | 处置动作 |
|---|---|---|
| 期限风险 | 已逾期 / 1 天内到期且进度 < 80%，关键路径任务自动升为高风险 | 登记风险 |
| 依赖阻塞 | 前置任务未完成，含跨 Sprint、依赖环路、下游传播链展示 | 标记阻塞 |
| 成员负载 | 剩余工时超过周期可用容量（按工作日折算），标出关键路径任务 | 登记风险 |
| 范围容量 | 计划 Story Point 超出 Sprint 容量 | 登记风险 |
| 成果缺失 | 状态 review / done 但无成果说明与提交记录 | 发提醒讨论 |
| 验收缺失 | Story 无验收标准，无法进入验收 | 发提醒讨论 |

每条事件展示：严重程度、判断依据、触发规则、处置方向。模型只负责生成"AI 解读"措辞，诊断结论全由规则决定；模型不可用时自动降级为规则文案。

### 2. 建议审批流（Proposal，不做独立页面）

- 按需入口：任务详情、Story 详情、Sprint 页的「AI 事件分析」块，点"分析"即扫当前上下文；
- 生成建议后进入待确认区，可逐条采纳 / 全部采纳 / 忽略（含原因），人工可改单个动作的值且保留 AI 原始建议；
- 待确认中心在顶栏铃铛，带未处理数量角标，会议型建议同样汇集于此；
- 支持链式创建：先建任务再建子任务，后续动作自动引用前置动作的真实 ID。

### 3. 执行可靠性

- 执行前复验：每个动作带 precondition，数据被改过则标 `stale` 并阻断，全 stale 显示"已失效"，与真失败区分；
- 依赖拓扑执行：按 `dependsOnActionIds` 排序，环路直接标 stale，不死循环；
- 双层审计：`proposals` 存完整生命周期，`ChangeHistory` 只记实际落库修改并可双向追溯（`source: "agent"` + `proposalId` + `proposalActionId`）；
- 与会议侧共用同一套 Proposal 协议与执行器（以 `AGENT_INTEGRATION_CONTRACT.md` 为准，已合并，无两套实现）。

### 4. 跨页面联动

甘特图 / 看板 / 故事地图的任务行显示 `AI n` 徽标（按最高严重程度着色，悬停看事件标题）。任务状态修复后重扫，徽标自动消失。

## 二、验证结果

- 自动化：7 个测试文件、102 个测试通过；类型检查与生产构建通过。
- 模型通道：`/api/meeting-llm` 200 且已配置；端到端解释调用 200，0 重试；输出遵守约束（不编造依赖、不做虚假按时承诺）。
- 人工验证（6 步，http://localhost:8443/）：
  1. Sprint 扫描出 10+ 条事件，无报错；
  2. 生成建议并显示模型解读；
  3. 执行后风险登记册新增对应风险；
  4. 顶栏中心执行 / 忽略正常；
  5. 执行前改任务状态，动作变 stale（"已执行 0 项，失效 1 项"）；
  6. 甘特图徽标正常；已完成任务重扫后旧事件消失，成果为空时正确保留提醒。
- 验证中修复两个体验问题：规则文案"建议"改名"处置方向"；整单展示拆分"已失效"与"失败"。

## 三、与会议侧的关系

- 共用协议与执行器，事件侧 `origin: "event"`，会议侧 `origin: "meeting"`，待确认中心天然兼容两边；
- 复用会议侧模型服务、路由与用量统计，未另起通道；
- 未做会议侧专属能力（材料中心、数字成员、纪要），按分工归会议侧所有。

## 四、已知限制

- 最终复验仅做 precondition 对比，不重算排期与容量（事件建议基本单动作，可接受；合分支后可复用会议侧重算逻辑）；
- 事件结果只在内存，切页面后需重扫（建议持久化并自动关联）；
- 控制台外部字体加载失败仅影响字体降级，无功能影响。
